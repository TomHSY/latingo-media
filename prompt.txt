LatinGo Autonomous Media Engine — System Design Objective

You are helping design and implement the media automation architecture for LatinGo, a local SBK (Salsa, Bachata, Kizomba) mobile application built with:

- Frontend: React Native (Expo) — mobile app
- Backend: FastAPI (Python) — REST API
- Database: PostgreSQL (AWS RDS, eu-north-1)
- Hosting: AWS Elastic Beanstalk
- Image storage: Cloudflare R2
- Scraper: AWS Lambda + GPT-4 extraction
- Admin: React + Vite + Tailwind CSS

Desired Architecture

Source of Truth

PostgreSQL event database, running in AWS Elastic Beanstalk (eu-north-1).

Actual Event model (SQLAlchemy):

{
  "id": "uuid",
  "title": "string (required)",
  "description": "string | null",
  "start_datetime": "datetime UTC (required)",
  "end_datetime": "datetime UTC (required)",
  "latitude": "float | null",
  "longitude": "float | null",
  "address": "string | null",
  "city": "string | null",
  "image_url": "string | null (R2 public URL or Facebook proxy URL)",
  "source_url": "string | null (Facebook event URL, unique)",
  "website_url": "string | null",
  "ticket_url": "string | null",
  "created_by": "user_id (FK)",
  "created_at": "datetime UTC",
  "dance_types": [
    { "id": "uuid", "slug": "salsa", "label_fr": "Salsa", "is_active": true }
  ]
}

IMPORTANT: dance_types is a MANY-TO-MANY relationship (not a single string).
A single event often has multiple dance types (e.g. "Salsa + Bachata + Kizomba").
Templates must handle 1 to 7 dance type pills per event.

Additional data available per event:
- rsvp_count (integer) — number of users interested/going. Can be used as a "popularity" signal for content selection.

API Endpoint for Media Pipeline

The existing REST API already supports everything the media pipeline needs:

GET /events?date_from=<ISO>&date_to=<ISO>&sort_by=date_asc

Available query params:
- city: string (ilike filter)
- dance_type: string (slug, e.g. "salsa")
- date_from: datetime ISO
- date_to: datetime ISO
- lat / lng / radius_km: GPS-based radius filter (Haversine)
- sort_by: "date_asc" | "date_desc" | "newest"
- include_past: boolean (default false)

Response includes full dance_types[] array with slug and label_fr per event.

Example query for weekend digest:
GET /events?date_from=2026-05-29T00:00:00Z&date_to=2026-05-31T23:59:59Z&sort_by=date_asc

API base URL: https://api.latingo.fr
Auth: POST /auth/login → Bearer token (admin account needed for full access)

Image Infrastructure

Event images come from two sources:
1. Facebook scraping → proxied through Cloudflare Worker (latingo-img-proxy)
   Format: https://latingo-img-proxy.tomhadrian-sy.workers.dev/?url={encoded_fb_url}
2. Direct uploads → Cloudflare R2 bucket
   Public URL base: https://pub-0a74468ba5af4a029f562126cdb5944f.r2.dev/{key}
   Bucket name: dance-app-event-images

Image quality varies significantly:
- Some are high-res event posters (1080px+)
- Some are small/blurry Facebook thumbnails
- Some are NULL (no image at all)

The rendering templates MUST handle all 3 cases gracefully:
- High quality → use as background/hero
- Low quality → use smaller or with overlay blur
- Missing → use a branded fallback pattern (Noche colors + dance type color accent)

Generated media assets should also be stored on R2 (same infra, reuse existing upload logic: resize to max appropriate dimensions, JPEG/PNG).

Existing Digest Logic (Already Proven)

The backend already has a working `send_digest()` function that:
1. Queries all pending notifications grouped by user
2. Batch-loads events, users, push tokens
3. Builds email digests with event lists
4. Sends via Resend API + Expo Push

The social media pipeline is essentially the PUBLIC-FACING version of this same logic:
- Same data source
- Same grouping logic (by day, by city, by dance type)
- Different output: visual media instead of email HTML

The email digest template already uses DM Sans font and structures events as: title + date + city.

---

Scraper Pipeline & Event Freshness

Events flow into the database via:
Google Sheet (curated URLs) → Lambda scraper → Facebook HTML parsing → GPT extraction → API POST → PostgreSQL

Key timing facts:
- Events are scraped/imported throughout the week
- Most events are added to DB 2-7 days before they happen
- Thursday generation for weekend content makes perfect sense (data already present)
- Some events are multi-day (festivals) — start_datetime and end_datetime can span several days

Image processing during scrape:
- Facebook cover images are downloaded, resized (max 800px), uploaded to R2
- Some events use poster images extracted via GPT vision from Google Drive

Competitive Positioning for Social Media

Context on the local social media dance scene:
- Local dance schools and associations already post their own events on Facebook/Instagram
- Some aggregator pages exist but are manual and inconsistent
- Facebook groups ("Danse SBK Pays Basque", etc.) are the current reference

LatinGo's competitive edge for social media:
- AGGREGATION: all events in one place (not just one school's events)
- RELIABILITY: data is structured, verified, always up-to-date
- CONSISTENCY: same format every week, predictable publishing
- NEUTRALITY: not promoting one organizer over another

Positioning strategy:
- Be the "service public" of SBK event information
- Format: "Où danser ce week-end ?" (informational) NOT "Come to this amazing party!" (promotional)
- Let the completeness and consistency build trust over time
- Never compete with organizers' own promotion — complement it

Content hierarchy should be:
1. This week's events (digest format — the primary value)
2. Highlighted events (high RSVP count or notable)
3. City-specific stories ("Ce soir à Bayonne")
4. Dance-type focused ("Les soirées Bachata du mois")
